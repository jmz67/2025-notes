在第一章中，我带你认识了 Redis，了解了它是什么，它能做什么。这一章，我们继续深入探索，看看 Redis 在各种 Web 应用中能派上什么用场。我会通过一些例子来说明，虽然这些例子比现实情况简单一些，但其实你只要稍作修改，就可以直接应用到你自己的项目里。

这一章主要是一本“Redis 实战指南”，而下一章（第三章）会更像一个命令参考手册，供你查阅。

我们先从宏观上看一下“Web 应用”到底是怎么回事。简单来说，就是一个服务器（或者一项服务），它通过 HTTP 协议接收网页浏览器发来的请求，然后返回响应。一个典型的 Web 服务器响应流程大概是这样的：

1. 首先，服务器接收到请求后会先解析它；
2. 然后，它会把请求交给预设好的“处理器”来处理；
3. 接着，处理器可能需要去数据库里查数据；
4. 拿到数据后，处理器会用这些数据来生成网页内容；
5. 最后，这些内容被打包成响应返回给用户的浏览器。

整个流程听起来挺简单的吧？而且，这种请求处理是“无状态”的 —— 意思是服务器不会记住你之前访问过什么，这样做的好处是：如果某台服务器坏了，换一台也没关系，系统更稳定。

当然，关于这个流程的每一步都可以优化，已经有不少书专门讲这些。而这本书的不同之处在于，它会告诉你怎么把一部分原本要通过传统数据库处理的操作，改成用 Redis 来处理，让速度更快、资源更省。还会介绍一些用传统数据库难以实现的功能，怎么用 Redis 搞定。

在这一章里，我们会通过一个“假想的大型电商网站”来说明这些问题怎么解决。我们叫它 “Fake Web Retailer”（虚拟电商平台）。它每天大约有 1 亿次访问请求，500 万个独立用户，每天卖出超过 10 万件商品！虽然这是个“假”的网站，数据听起来也很吓人，但正是因为能解决这么大的问题，小问题自然就不在话下。而且除了一个特例之外，其他所有的方案都可以通过一台只装了几 GB 内存的 Redis 服务器来完成！这些方案的目标是让网站在实时响应用户请求时，能跑得更快更稳。

本章中的每个方案，或者它们的变种，其实都在真实项目中被用过，效果非常好。通过把一部分处理任务交给 Redis，我们大大减轻了数据库的压力，页面加载得更快，系统也更高效。

我们要面对的第一个问题是：**如何用 Redis 来管理用户的登录会话。**

## 2.1 登陆和 Cookie 缓存
---
每当我们登陆网上服务，比如银行账户、邮箱等，系统都会通过 Cookie 来记住我们是谁。Cookie 是网站要求浏览器保存的一小段数据，每次访问这个网站时浏览器都会自动把它带上。

对于登录这类场景，Cookie 通常有两种存储用户信息的方式：
**签名型 Cookie（signed cookie）** 和 **令牌型 Cookie（token cookie）**。

签名型 Cookie 会直接在 Cookie 里保存用户信息，比如用户名、用户 ID、上次登录时间等等。它还会附带一个签名，用于验证这些信息有没有被篡改过，比如防止有人偷偷把用户名改成别人。

而令牌型 Cookie 就更简单了，它只是一串随机字节。服务器收到这个 token 后，会在数据库中查找对应的用户信息。时间久了的旧 token 也可以清理掉，腾出空间给新的用户用。

下面这张表总结了这两种方式的优缺点，但为了不自己去写复杂的签名机制，我们的主角 —— Fake Web Retailer 选择了更简单的 token cookie 方案：把用户登录信息存在数据库中，用 Cookie 里的 token 去查。

这样一来，他们还可以顺便记录用户的浏览时间、看了多少商品，之后做用户行为分析、个性化推荐啥的。

不过问题也来了：用户通常会反复浏览很多商品，记录这些操作会导致数据库频繁写入，压力很大。而且即使你对数据库做了各种优化，大多数关系型数据库的写入能力也就每秒处理几百到几千行而已。

举个例子，Fake Web Retailer 每秒平均有 1200 次写入，高峰时甚至接近 6000 次！他们不得不部署了 **10 台数据库服务器**才能顶住流量。现在，我们的任务是：**把这些登录相关的写入操作，从数据库挪到 Redis 上去**！

### 使用 redis 管理登陆会话
---
我们的做法是这样的：
- 用 Redis 的 `HASH` 类型，建立从登录 token 到用户的映射；   
- 每次收到请求，就查一下这个 token 对应的是谁；   
- 如果用户正在浏览商品，就顺便更新一些信息：
    
    1. 在 login 的 `HASH` 中更新时间戳；      
    2. 把这个用户添加到一个记录最近活跃用户的 `ZSET` 中；       
    3. 如果他们看了商品，就把商品 ID 加到用户的「最近浏览商品」`ZSET` 里；  
    4. 如果这个列表超过了 25 个商品，就裁剪掉最早看的那些。

听起来不复杂，对吧？但就是这样一个看起来简单的设计，在现代服务器上，每秒可以轻松处理 **2 万次商品浏览记录**，比原来的数据库方案快了 **三倍还多**！而且后面我们还会教你怎么让它再快一倍。

### 清理旧数据
---
随着时间推移，Redis 占用的内存会越来越大，所以我们需要定期清理旧的登录信息。我们的策略是：**最多只保留最近 1000 万个登录会话**。

具体步骤：
1. 查看最近活跃用户的 `ZSET` 长度；
2. 如果太长了，就一次取出最旧的 100 个；
3. 从 ZSET 删除这些 token；
4. 从 login 的 `HASH` 删除它们；
5. 顺便也删掉该用户的浏览记录 `ZSET`；
6. 如果 ZSET 不太长，就等一秒再试。

你可能在想：这么简单的逻辑，真能撑住五百万用户每天访问吗？

别担心，我们来算一笔账：

- 一天有 86400 秒；
- 假设每天有 500 万用户，那平均每秒新增不到 58 个 session；
- 而我们的清理函数，每秒可以清掉超过 **一万个 token**（甚至本地可以超过 6 万），性能绰绰有余，完全是“高配打低功”。

### 关于清理函数的运行方式
---
书里的清理函数一般是写成一个守护进程（daemon），也可以配置成定时任务（cron job）运行，有的甚至可以在每次用户操作时顺手清理一下。你会看到类似 `while not QUIT:` 的写法，就是提示这个函数是要常驻后台运行的。

守护进程是指一种常驻后台运行的程序，它会一直运行，不会主动退出，通常用于持续监听或定时执行某些任务，比如：日志收集器，系统监控工具，清理过期数据的服务（比如下面的代码）

```python
QUIT = False                 # 控制守护进程是否退出的标志变量，默认不断循环
LIMIT = 10000000            # 最多允许存在的活跃 session 数（也就是 recent: ZSET 的最大长度）

def clean_sessions(conn):   # 定义清理函数，接收 Redis 连接对象 conn
    while not QUIT:         # 如果 QUIT 为 False，就一直循环运行，相当于一个后台服务
        size = conn.zcard('recent:')  # 获取 'recent:' ZSET 的当前大小（有多少 token）
        
        if size <= LIMIT:   # 如果还没超过设定的最大值，就不用清理
            time.sleep(1)   # 等待一秒，再继续检查
            continue        # 回到循环开头，重新判断
        
        end_index = min(size - LIMIT, 100)  
        # 计算要清理多少个最旧的 token，最多清理 100 个
        
        tokens = conn.zrange('recent:', 0, end_index - 1)
        # 获取需要删除的 token（ZSET 中最早添加的前 N 个）
        
        session_keys = ['viewed:' + token for token in tokens]
        # 构建每个用户对应的“最近浏览商品”的 key，如 viewed:token123
        
        conn.delete(*session_keys)
        # 删除这些“最近浏览商品”的记录（ZSET 类型）
        
        conn.hdel('login:', *tokens)
        # 从 login: 哈希表中删除这些用户的登录 token 映射
        
        conn.zrem('recent:', *tokens)
        # 从 recent: ZSET 中删除这些最老的 token，完成清理
```

### 一些技术小贴士
---
-   Python 中像 `conn.delete(*vtokens)` 这样的语法，其实是把多个参数打包传进去，感兴趣可以看 Python 教程。
-   Redis 其实还有一种方法叫 `EXPIRE`，可以给 key 设置自动过期时间。但我们这次没用，是因为我们要手动控制最多保留 1000 万会话，并且有时候还要分析“被遗弃的购物车”，这样 `EXPIRE` 就不够灵活。

当然啦，真正懂并发编程的朋友可能会说：这个清理函数存在「竞争条件」，比如用户刚好在我们清理他的时候重新访问了页面。但别担心，这种情况极少发生，就算发生了，最多也就是让他重新登录一次，对整体数据没啥影响。

我们现在已经大大减少了对数据库的写入量，每天省下了上百万次写操作！这只是使用 Redis 的第一步，接下来我们还会讲讲 Redis 在其他类型的 Cookie 处理上的用法。
